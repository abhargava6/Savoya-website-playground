Today's modification handling is all-or-nothing

🔒
Mod Pending split is hardcoded. Some fields already skip Mod Pending, but the list can't be changed without a code deploy. Some fields are in a gray zone ("Sometimes").
🚫
Non-Mod Pending changes are completely silent. When a field doesn't trigger Mod Pending, no email goes out at all. Clients and vendors don't know anything changed.
⚠️
Mod Pending emails have no content. Clients see "your reservation was modified" with no detail on what changed, who did it, or why. They call in.
📩
Vendors get Accept/Reject for everything. When Mod Pending fires, vendors receive Accept/Reject even for changes irrelevant to them. Sometimes forget to accept, blocking the reservation.
🔥
No middle ground. It's either full Mod Pending + blank emails to everyone, or complete silence. No way to notify just the client, just the vendor, or show what actually changed.

Three changes fix this

1

Configurable Mod Pending

The Mod Pending split already exists, but it's hardcoded. Now the field list is configurable without a code deploy.

2

Granular Email Routing

Non-Mod Pending changes are no longer silent. Per-field control over who gets notified: client, vendor, both, or neither.

3

Emails With Content

All emails show old → new values. Client emails show who changed it and who requested it. Vendors get Accept/Reject or Acknowledge.

All three lists are configurable without code changes. The Mod Pending list (25 fields), no-client-email list (2 fields), and no-vendor-email list (10 fields) operate independently to control status and email routing per field.

Client emails now show what changed

Key rules

  • • Email only if a field outside the "no client email" list changed
  • • Shows old → new values for each changed field
  • • Max 3 changes inline; beyond that, a CTA links to a PDF
  • • Display order: Itinerary → Reservation Details → Billing → Notifications
  • • "Changed by Savoya" or client's name
  • • Optional "Requested by" tag from internal users
  • • Override: "Do not send" checkbox

Two vendor email types

Accept / Reject

When: an itinerary-impacting field changes (reservation goes to Mod Pending)

Includes old → new values. Vendor must accept or reject. Reservation stays in Mod Pending until they respond.

Shows: Itinerary + Reservation Details fields only

ACCEPT / REJECT

Acknowledge

When: non-impacting field changes that still warrant notification

Includes old → new values. One-click acknowledge. Does not block the reservation.

Shows: Itinerary + Reservation Details fields only

ACKNOWLEDGE CHANGE

Both types: max 3 changes inline, PDF overflow beyond 3. Only the most recent edit event is shown.

Three independent, configurable lists

25

Non-Itinerary Impacting

Controls: Mod Pending status
TC Name, Passenger Note, Reference Number, Signage, Travel Bank, Payment, Add to Group, Pickup Note, Dropoff Country, and more...
2

No Client Email

Controls: Client email send + field visibility in email
Reservation Note, Greeter Required for Pickup
10

No Vendor Email

Controls: Vendor email send + field visibility in email
TC Name, Additional Notifications, Passenger Notifications, Payment, Signage, Add to Group, Reference Number, Travel Bank, Reservation Note, Greeter Required for Pickup

All three lists are independent. A field can be in one, two, or all three. Fields in both "no client email" and "no vendor email" lists are effectively silent.
